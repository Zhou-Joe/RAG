# 上传队列与向量化恢复

上传成功后文档进入排队状态，同一部署主机一次处理一份文档。排队记录使用业务数据库中的 Document 状态，不依赖页面连接。ASGI 服务启动时通过 `data/ingestion.lock` 获取主机锁，将中断的 OCR/向量化任务恢复为待处理，再按创建顺序继续；失败任务需点击「重试（继续进度）」。同一份文档重复提交重试返回 409。

向量化按小批次写入 Chroma，而非全部计算结束后一次写入。片段 ID 由文档标识、向量配置指纹、片段顺序和内容生成；重试读取已存在的 ID，跳过成功片段，未成功片段继续计算。同一 ID 的写入为 upsert，因此网络中断后结果不确定的请求也不会追加重复向量。

WeMM 默认每批最多 4 条、读取等待 180 秒，参数为 `WEMM_BATCH_SIZE` 和 `WEMM_REQUEST_TIMEOUT`。遇到超时、429 或 5xx 时，仅允许将失败批次拆成两个半批，各重试一次；半批继续失败则结束任务并保留成功进度，不无限重试。认证、地址、维度等错误直接失败。服务持续停机或长时间不响应仍可能失败，此时明确显示原因并提供重试入口。

OCR 结果已保存时，重试直接使用保存的正文、图片和版面数据；OCR 尚未完成时需重新解析。关键词索引成功后才标记完成，关键词写入失败不会清空已经保存的向量。管理页显示批次保存进度，失败任务不发布为已完成。

集合记录向量配置指纹。更改模型、向量维度或端点后，已有新格式集合需显式重建，不允许混用不同配置的片段。重建和删除使用 Chroma 的集合接口，保留打开的 SQLite 文件，避免 1032 错误。

## 部署与边界

本次无需数据库迁移。更新代码后等待当前任务结束，重启 ASGI Web 即可。`FOS_INGESTION_WORKER=0` 仅关闭 ASGI 启动时的自动恢复；上传请求仍会启动队列。主机锁适用于 Mac/Linux，同一数据目录的多个进程共享同一个锁；多台服务器需要共享任务系统，不在本次范围。聊天仍遵守原有单 ASGI Web 进程约束。

管理命令的显式整库重建不属于上传队列。运行 `reindex_clean` 或 `reindex_failed` 前应暂停 Web 入库，避免管理员重建与上传争用同一库。`reindex_failed` 是清理后恢复的管理命令；日常失败恢复使用页面上的续传按钮，才能保留批次检查点。

回退时先停止 Web 并备份数据库、Chroma 和关键词索引。新文本 ID 使用 `ingest-` 前缀，现有出处字段与路由支持该 ID，无需修改旧引用。旧代码仍可读取新索引，但无法提供新的分批续传功能。

## 验证

196 项 Django 与 23 项 Node 回归通过。覆盖：两个工作线程争用主机锁时仅串行处理、任务原子认领、防重复重试、重启状态恢复、复用保存 OCR、真实 Chroma 中断后续传、重复写入无新增向量、仅缩小失败批次、不可重试错误直接失败、关键词写入失败后续传、模型变化阻止混用、部门权限和 CSRF、任务异常不堵塞队列。测试使用临时目录与模拟向量服务，不宣称所有真实模型服务均通过压力验收。
